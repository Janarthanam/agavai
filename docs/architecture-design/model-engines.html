Whistle hears. Needle routes. Qwen decides.

Whistle can turn speech into text. Needle can choose which group of tools Qwen sees. Qwen still chooses the action, handles the tool result and writes the spoken answer.

Proposed worker, not implemented

One request: “Open the browser”

  1. The speech worker produces the words.Microphone audio → “open the browser”. Words appear on screen while you speak; they cannot trigger an action.
  2. The session waits for the sentence to finish.
  3. The router selects the relevant tool group.
  4. Qwen chooses a tool; the session runs it.Request + launch-tool definitions → Qwen → launch(target="browser") → the session's allowlist → desktop command.
  5. Qwen reads the result and writes the answer.Desktop result → session → Qwen → “Browser opened.” A tool request usually needs this second Qwen call.
  6. Kokoro turns that answer into audio.“Browser opened.” → Kokoro → WAV file → audio player → speakers. The session then listens for the next request.

What changes in the code—and what stays
  • Speech recognition: add a Whistle worker behind the same audio-in/text-events-out interface as Parakeet. Select the worker and its model files in ASR configuration. Whistle's roughly one-second chunks are not a measured first-word latency.
  • Routing: implement Needle behind the existing select(utterance) → head IDs interface. It selects a group such as launch; it does not execute Needle-generated desktop actions.
  • Engines: Parakeet uses ONNX Runtime; Whistle and Needle use Cactus's native runtime and different model files. Changing a weights path alone cannot swap engines. Whistle and Needle need separate workers because the inspected Cactus binding stores one loaded model per process.
  • Qwen: stays on llama-server. Its GGUF weights are already configurable. Needle cannot replace conversation handling and answer generation in this design.
  • Testing: compare transcription accuracy separately from turn-ending behavior, and compare Needle routing against keyword/Jev routing. Record the selected engine, model hashes and endpoint policy so the runs are comparable.
Process lifetimes and the data crossing each boundary
  • Session: one agavai listen process owns conversation, confirmations and the tool allowlist. Audio pumping and worker readers are threads inside it. A follow-up with history can make a Qwen context-classification call before routing; exact controls such as Yes/No can bypass models.
  • Capture / speech worker: parec opens per utterance; the model worker stays loaded for the listening session. Audio passes through the session to the worker as length-prefixed 16 kHz mono PCM. Worker responses are JSON lines: partial text, boundary/end events, ready, reset or error. The diagram shortens this to “audio → words”.
  • Router: Jev is a remote HTTPS service; keyword fallback runs inside the session. Proposed Needle is a session-owned local child with JSON request/response pipes. A missing or failed candidate worker must be reported; it must not silently be scored as Needle while using keywords.
  • Qwen: a separate, long-running llama-server process. The session exchanges messages, tool definitions, tool calls and replies over localhost HTTP on port 18766. Neither the router nor Qwen executes desktop commands.
  • Desktop commands: spawned by the session's allowlisted tool functions when needed. Results return to the session, then to Qwen; tool functions also publish UI results.
  • Overlay: a separate Quickshell process watches ui.json for partial words, tool progress and results. Its stop/cancel controls signal the session through the CLI.
  • Speech / playback: Kokoro is a warm local process with a 600 s idle timeout. Reply text goes over a Unix socket; synthesized audio is written to a WAV. A separate pw-play or paplay child plays it. Cancel stops that playback; spoken interruption is not implemented. Kokoro failure falls back to eSpeak, then notification.
  • Local candidate setup: pin model/library files, pass explicit local weights and NEEDLE3_LIB_PATH, set NEEDLE_TELEMETRY=0 and HF_HUB_OFFLINE=1. Disable automatic date injection for frozen-clock evals.
Evidence and sources

The process layout follows the current audio contract, session flow and implementation: ASR parent, router, orchestrator, Qwen client, speech client, Kokoro worker.

The latency values come from the stored report; targets come from eval budgets. They are not SLAs. Warm Kokoro synthesis alone took 0.49–0.73 s for the short measured replies. Jev's documented 70–500 ms is not a local benchmark.

Candidate roles and runtime constraints come from the 2026-10-21 package-source investigation in this thread: Whistle, Needle, cactus-needle. Recheck the pinned package at implementation time. This document proposes integration; it does not implement it.
